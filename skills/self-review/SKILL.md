# セルフレビュー

委譲された実装を終えたサブエージェントが、自分の作業の最後に使う。
実装した本人は経緯や試行錯誤を知っているため、差分を「読めば分かるもの」として見てしまう。
そこでレビューは新しいサブエージェント（レビュアー）に任せ、差分と判断に必要な前提だけを渡す。
指摘への対応と報告は、使った本人が行う。

サブエージェントツールが使えない、または上位の指示で委譲が制限されている場合は、同じ観点で自分の差分をレビューし、独立レビューを実施できなかったことを報告する。レビューのために権限を広げたり別の CLI セッションを勝手に起動したりしない。

作業原則のパスは CODEX_HOME（未設定なら ~/.codex）を使って絶対パスへ展開する。

## 手順

1. **渡す材料を集める。**
   - 目的と受入条件（自分が受けた委譲文から。ユーザー要件はそのまま）
   - 差分の取り方（例: `git -C <path> diff <base>...HEAD`）。未コミットがあれば `git diff` も
   - 守るべき制約（対象外、触ってはいけない範囲、確定済みの決定）
   - 実施した検証（コマンドと結果。解釈は付けない）
   - 関連ドキュメントや issue の所在が分かっていれば、その場所（中身の要約ではなく）
2. **渡さないもの。** 実装の経緯、却下した案、自分の評価や「ここは問題ない」という説明。レビュアーが差分とリポジトリから自分で判断できるようにする。
3. **利用可能な Codex のサブエージェント起動ツールでレビュアーを起動する**。依頼文は下の「レビュー依頼」を使う。差分が大きく観点が広い場合は観点ごとに並列で起動してよいが、全員に同じ目的・制約を渡し、うち一人には全体の方向（目的と前提・構造）を担当させる。
4. **結果を処理する。**
   - 必須修正は自分で直してコミットし、修正後の差分で再レビューする（新しいレビュアーに、前回の指摘と対応を添えて渡す）。再レビューは2回までとし、それでも残る指摘は未解決事項にする。
   - 提案は委譲範囲内で採否を判断し、見送るなら理由を残す。
   - 確認事項は調べて決着させる。委譲範囲を超える判断が必要なら、直さずに親への報告で判断を仰ぐ。
5. **最終報告に含める。** 親エージェントへの最終報告（ハンドバック）の検証欄に、レビュー結果、対応内容とコミット、見送った指摘とその理由、未解決・未確認の事項を書く。

## レビュー依頼

以下を埋めてサブエージェントに渡す。

```
開始前に <${CODEX_HOME:-~/.codex}/subagent-working-principles.md の絶対パス> を読み、従うこと。
あなたは次の変更のレビュアーです。ファイルの変更・コミット・push はしないこと。

## 目的と受入条件
<...>
## 制約
<...>
## 差分
<リポジトリのパスと diff の取り方>
## 実施済みの検証
<コマンドと結果>
## 関連する場所（分かっている範囲）
<ドキュメント、issue、PR の場所。なければ「なし」>

## 観点
判断の軸は、未来の変更者が「どこを直すべきか」「何が起きるか」「なぜそうなっているか」に迷わないかである。
正しさ・安全性・データ保全などの必須条件を先に満たし、そのうえで不要な概念・状態・判断が少ないかを見る。
目的と前提 → 構造 → 細部の順に見る。進む方向がずれているなら、命名や書式の指摘で済ませない。
設計や方針の問題は、各分類の中で細部の指摘より先に挙げる。方針を変えるべきなら、変われば書き直しになる細部の指摘は省いてよい。

1. 正しさ: 目的と受入条件を満たすか。失敗時・境界値・権限・外部入力の扱いは安全か。テストは内部実装ではなく観測可能な振る舞いを固定しているか。
2. 将来像との整合: 関連ドキュメント、README、設計メモ、open な issue・PR を自分で探して読み、将来の方向を把握する。この変更がそれと矛盾したり、移行を難しくしたりしていないか。逆に、未確定の将来のために拡張点や抽象を先回りで足していないか。確定した将来要件は今の設計を評価する材料であり、今実装する命令ではない。
3. 既知の解法との比較: 問題を抽象化し、同じ構造の問題を扱う他の事例（このリポジトリ内の既存実装、標準ライブラリ、主要な OSS、確立した設計パターン）と比べる。一般的な解き方から外れているなら、外れる理由が制約から説明できるか。既存実装にあるという理由だけで不適切な構造を踏襲していないか。
4. シンプルさ: 解き方の都合で持ち込んだ複雑さがないか。
   - 新しいモード・フラグ・例外処理は、問題の本質から来ているか、責務の置き場所が合っていないせいか。
   - 使われない引数、省略可能にする必要のない値、到達しない分岐、根拠のない設定が残っていないか。型や構造で閉じられる自由度は閉じているか。
   - 同じ知識やルールが複数箇所で独立して管理されていないか。逆に、変更理由が異なるものを見た目だけで共通化していないか。
   - 名前・型・データの流れで挙動が分かるか。コメントが「何をしているか」の説明で構造の分かりにくさを補っていないか（「なぜ」の記録は良い）。
   - 行数や分岐数ではなく、読み手が判断しなければならないことの量で測る。
5. 運用（該当する場合）: 失敗を検知でき、どこまで進んだか・どこから再開できるかが分かるか。回復手段のない破壊的変更をしていないか。

## 指摘の書き方
- 分類: 必須修正（要求・安全・確定した規約への不適合）／提案（現状も条件は満たすが改善できる）／確認事項（判断材料が足りない）。好みや軽微な書式の指摘は必須修正に混ぜず提案とし、取り込みを止める理由にしない。必須条件に関わる未確認は、適合とみなさず確認事項にする。
- 各指摘は「事実（ファイル:行）→ 根拠 → 具体的な影響 → 修正の方向」で書く。「複雑だ」だけで終わらせない。修正手段の指定は必要な場合に限る。
- 変更と無関係な全面改修は求めない。

## 出力
1. 結論: このまま取り込めるか、修正が必要か
2. 指摘一覧（上の分類ごと）
3. 観点ごとに確認した範囲（読んだドキュメント・issue、比較した事例）と、確認できなかったこと
```
